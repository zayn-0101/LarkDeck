## 二、这个项目的头号失败模式是「静默」

不报错的失败比报错的失败贵得多。已经踩过的静默坑：

- **按钮点了没反应** —— 1.0 的 `action` 容器混进 2.0 卡，飞书拒收但不报错；
- **折叠面板退化成普通行** —— `header.title` 塞了 `lark_md`，或者没给 `icon`
  （没有 icon 就没有展开控件，面板变成一个永远打不开的抽屉）；
- **配置写了不生效** —— 键路径写错就等于没有读取路径，YAML 全部空转；
- **钩子没挂上** —— 只是页脚少两段、面板空着，卡片照常渲染，从表面看不出来；
- **每一帧卡片更新都失败** —— `message.update` 拒收 `interactive`，而失败会**回落**成内置
  文本编辑：消息照样发出去，只在 WARNING 级留一行，很容易以为一切正常；
- **面板永久不渲染**（2026-09-12 实际踩过并回退）—— 曾想用 `turn_id` 把卡片和会话精确对上，
  但两侧的 `turn_id` 是**两个不相干的命名空间**：钩子载荷给的是 agent 的
  `_current_turn_id`，而 `send_stream_frame()` 收到的是 stream consumer 现生成的裸
  `uuid4()`。join 永远匹配不上，面板直接消失，**且不报任何错**。
  代码里的警告块见 `core/panel.py::snapshot`。
- **整条回答被渲染成一个空格**（2026-09-12 实际踩过并移除该特性）—— 「叙述归档」用裸分隔符
  `"\n\n---\n"` 猜核心有没有往帧里拼工具进度块。但核心的合成式是
  `"\n\n---\n".join(p for p in (accumulated, progress) if p)`：**没有工具进度时帧文本就是
  累积正文本身**。而 `---` 独占行正是普通 markdown 分隔线，模型随时会写。一旦误判，
  归档点被推到分隔线处 → 之后每帧都算不出正文 → 卡片被刷空 → finalize 的
  `display or " "` 让答案只剩一个空格。**而核心按完整帧文本乐观记账、判定「已送达」，
  不会再补发** —— 答案彻底消失，任何一层都不报错。
  教训：**当一段文本既可能是「系统生成的元数据」又可能是「用户内容」时，不要用字符串
  匹配去猜**；判错两个方向都会吞内容，那就选不猜。详见 `core/adapter.py` 顶部说明。
- **卡片在真机上根本发不出去，本地门禁全绿**（2026-09-13 实际踩过）—— 2.0 的
  `card(title=...)` 把 `i18n_text()` 返回的**节点**直接塞进 `plain_text.content`，产出
  `{"content": {"tag": "plain_text", ...}}` 这种嵌套结构；飞书整张卡拒收
  （`230099 / ErrCode 200621 parse card json err`）。1.0 的 `legacy_card` 一直处理正确，
  所以**只有走 2.0 的澄清卡**中招 —— 而它们本地单测只核「有没有 header」，完全看不出来。
  教训：**能被本地规则判定的卡片合法性，就该在本地钉住**（现在是
  `test_every_text_node_carries_a_string_not_a_nested_node`：所有文本节点的 `content`
  与 `i18n_content` 的值必须是字符串）；真机探针留给「只有 API 能裁决」的那部分
  （枚举值、元素上限、方言接受度）。
- **探针永远说「不支持」**（2026-09-12 实际踩过）—— 转发 `metadata` 给父类时写成
  `getattr(type(parent), "interrupt_session_activity", None)`，而 `parent` 是
  `super()` 对象、**`type(parent)` 恒为 `super`** ⇒ 探针拿不到方法、永远判 False，
  参数被静默丢掉。`super()` 对象要用 `getattr(parent, name)`（会沿 MRO 找到下一个实现）。
  同类：任何「探测函数签名」的代码，先确认你探的是**函数本身**而不是包装物。
- **门禁只核「字面形状」，从不走真实判据**（2026-09-13）—— 2.0 多选答案的断言原来是
  `json.loads(answer) == [...]`，于是「把答案改成根本不可能被接受的形态」照样全绿，
  而真机上用户「选完没反应」。同类还有：只断言「卡里出现过 behaviors 字样」，于是
  「少给一个组件挂 behaviors」也全绿。做法：**断言要走下游真正消费它的那个解码器**
  （`check_clarify_e2e.py` 现在直接调 `tools.clarify_tool._clean_answer` 验答案）。
- **门禁漏掉整条关键线路**（2026-09-12，变异测试查出来的）—— 把 `hooks.py` 里
  `kind == "text"` 那个分支整条删掉（于是「正文切断推理轮」永久失效、推理连成一个
  巨大的「第 1 轮」），**四个门禁全部照绿**。同一批还有 `adapter.py` 不传 `rounds=`、
  把 `panel_expanded` 写死 False —— 都没有任何断言。做法：每加一个特性，先把它**关键
  信号**那一行改坏，看门禁是否变红；不变红就补断言。

**推论 1：每加一层能力，都要顺手给它配一个「能自证」的东西。** 要么是门禁里的一条断言，
要么是限流的诊断日志（现有例子：`面板无数据` / `pre_tool_call 钩子触达` / `指标已接入`）。
不要拿「看起来是好的」结案。

**推论 2：跨层的「同名字段」必须先证明同源，再假设相等。** 上面那个 bug 的测试之所以
全绿，是因为测试里两边喂的是我自己传的同一个值 —— **测试把我的错误假设一起编码进去了**，
这叫自证循环。验证跨层契约只能去读**真实源码**里的取值点，或者写走真派发器的集成测试
（`check_hooks.py` 就是干这个的）。

**推论 3：状态类字段的「优先级」比取值更难，且错得很安静。** 回合结局要按
`interrupted > failed > completed` 判 —— 官方 `completed` 的表达式
（`agent/turn_finalizer.py`）里**没有** `interrupted`，所以「被中止但已产出部分正文」
的回合会同时 `completed=True, interrupted=True`；先看 `completed` 就会把中止显示成绿色
「已完成」。而这类错误肉眼几乎看不出来（谁会盯着「中止的那次是绿的」？）。
凡是「多个布尔标志合成一个状态」的地方，都要把优先级写成一行注释 + 一条门禁断言。

**推论 4：同一条业务规则在两条路径上可能有相反的结论 —— 别把 A 路的实测当成 B 路的。**
2026-09-13 实证：多选答案的形态，**文字回答**那条路径（`clarify_gateway`）会把 JSON 数组串
判成「无效选择」，而**卡片点击**那条路径（`resolve_gateway_clarify` → 工具侧
`_parse_multi_select_response`）对 JSON 与逗号串**都能解码**。审计报告里「JSON 一律被拒」
是 A 路的结论，差点让我把 B 路改坏。凡「某格式不被接受」的结论，都要问一句
**在哪条路径上、谁在解析**。

**推论 5：跨会话的状态写入必须在「归属」这一层就被挡住，而不是靠渲染时兜。**
`/stop` 的中止状态曾被打到**另一个会话**上：因为 `mark_stopped` 复用了「渲染用」的归属判据，
而那条判据允许「绑定的会话暂时没内容 → 退回最近活跃」。教训：**有绑定就是有归属**；
「暂时没内容」的表现应该是「这张卡没有面板」，绝不能是「换一个会话」。
同理，需要写状态的那条路径（`/stop`）应当**直按绑定取会话**，而不是借渲染的判据 ——
借来的判据会把它自己的宽松条件一起带进来。

**推论 6：断言要看**判别力**，不是「有没有断言」。** 2026-09-13 连续三轮审计各戳穿一条：
① 「父类不许被调用两次」那条断言里的假父类**永不抛异常**，而「双跑」只在父类**内部**抛时发生
—— 这条断言结构上不可能失败；② 「over-budget 档也要带打字机」我第一版用**默认值**去测，
而变异是「忘了把自定义参数传下去」⇒ 默认值恰好等于期望值，照样绿；
③ 第六轮我**自称**修好的 M22（`_positive` 的 nan/inf 保护），第七轮实测**仍然全绿** ——
那条「遍历坏值」的断言根本看不见 `_positive`（`nan` 走 `_positive→False` ⇒ 卡片里没有这个
字段 ⇒ `continue`；`inf` 走 `True` ⇒ 由 `streaming_config` 自己的 `try/except` 接住）。
**做法：补完断言先问一句「我要防的那个改动，是这一行能看见的吗」**，
再用变异实测一遍；看不见就换观测量（传自定义值 / 让假实现真的抛 / 直接打被保护的那一层）。
更不能把「已修」写进注释和文档 —— 那会让下一个人不再检查（本轮就发生了）。

**推论 7（第七轮阻断项）：改常量的「口径」时，必须 grep 出所有同名赋值，且回归 fixture 要贴着新阈值写。**
`_MAX_TRACKED_TEXT` 从 20000 字符改成字节口径时（中间版本写过 120000，最终定为
`_FEISHU_CARD_BYTE_LIMIT - _CARD_BYTES_OVERHEAD` = **126976**），文件里**旧的**
`_MAX_TRACKED_TEXT = _cards.CARD_BYTE_BUDGET`（40000）没删 ⇒ Python 后赋值覆盖前者 ⇒
整个修复是**死代码**，而那条回归用例的 fixture 恰好卡在 40000 上，**它的绿正是来自这句覆盖**
（删掉覆盖行，测试立刻变红）。两条制度性做法：① 形状断言 —— 现在有一条「阈值 + 卡片固定开销
≤ 飞书实测硬上限」；② 撤掉修复必须变红的**变异清单**固化在 `tests/mutate_check.py` 里，
不再依赖某一轮审计的临时脚本。

**推论 8：「空集 / 空列表 = 一切正常」型断言没有判别力 —— 要让被观测对象**真的缺东西**。**
`probe_report(真适配器)["missing_reactions"] == []` 看着在守「上游改名会报警」，
但把 `probe_report` 改成恒返回 `[]`（探测彻底失效）它照样绿。做法：**拿一个什么都没有的类
去探**，缺什么就必须如实报出什么。同理，「报告里**没有**这个键」与「这个键是空列表」
必须分开 —— 前者是探测失效，后者才是契约齐全。

**推论 9：门禁自己的「覆盖清单」不能是硬编码字面量。** `check_override.py` 里那份
「要检查哪些覆盖」的名字列表原来写死，从里面删掉 `_reactions_enabled` 没有任何门禁看得见
（第七轮实测全绿）。做法：清单**从 `compat` 的登记表派生**，单一事实来源只有一处。

**推论 10：断言要盯**副作用的内容**，不能只数它发生了没有。**
第七路审计的阻断项修好之后（正文存得下 ⇒ `/stop` 会发 patch 了），我加了一条回归断言
`assert updates` —— 它对着真机跑却抓不到任何东西：`/stop` 发出的 patch
**与屏幕上那张卡逐字节相同**（降载把承载状态色的面板整块摘掉了），用户看到的还是「没变色」。
是同一天新写的真机探针 `probe_render.py --stop-redraw` 把它抓出来的（它断言**载荷里有颜色**），
第八路审计独立复现了同一条（并指出「把 ①' 的断言对齐上面的 ① 就会红」）。
**做法：凡是「副作用应该改变用户看到的东西」，断言就要落在**载荷/内容**上，
并且尽量带一个对照（改前 vs 改后必须不同）。**

**推论 11：新写的「响亮失败」保证，自己也要有测试 —— 否则它随时会被静默改回去。**
第八路审计实测三例：yaml 解析器里那句 `raise AssertionError`（认不出的行直接失败）
退回 `continue` → 四门禁全绿；`mutate_check.py` 的基线守卫（当时还不存在）缺失时，
基线一红就「所有变异都被抓住」；`check_override.py` 自己的键清单删一项也全绿。
**做法：给「解析器/验证器/门禁」本身写输入（畸形样本 + 对照样本），
并把它们的核心保证也放进变异清单。**

**推论 12：常量也有「守卫」的责任 —— 只锁关系不够。**
第八路审计把 `_FEISHU_CARD_BYTE_LIMIT` 改成 999999、`_CARD_BYTES_OVERHEAD` 改成 50000、
`_MAX_TRACKED_TEXT` 改成手写 127000，**四门禁全绿**（因为断言只检查「阈值 + 开销 ≤ 硬上限」
这条**关系**，三个输入一起动就都成立；只动一个也可以恰好落在关系内）。
**做法：把实测来源写进断言**（真机包络线 `[128000, 160000)` 与出处），
把「余量必须是**小**余量」写成上界，把「阈值必须是算出来的」写成等式 ——
机械门禁证明不了那个实测数字，但能让改它的人**必须面对那份实测**。

**推论 13：同一件事的「判据」与「守卫」必须**同口径** —— 两个都对、合起来还是错。**
`_ld_note_text` 用正文**原始 utf-8 字节**判断「存不存得下」，而「这张卡装不装得下状态小面板」
的守卫用 **JSON 序列化后的字节**判。两边单看都没错，但 JSON 会把 `\n` `"` `\\` `\t` 转义成
两字节，于是合起来留了一条缝：正文被留下（⇒ `/stop` 必发 patch）、那张卡却装不下小面板
⇒ patch 发了、`code=0`、**载荷里没有任何颜色**，唯一日志还不提颜色。
第九路审计实测出这条缝（正文 126900 字节 + 300 换行），并顺手证明**老的两条断言拦不住它**
（把壳从 543 加到 1015 字节就重新撕开 303 字节的窗口，四门禁全绿）。
**做法：凡是「判 X 存不下」与「判 Y 装得下」出现在两处，先确认两者量的是同一个东西；
再补一条**端到端**断言把「判据成立 ⇒ 用户可见的结果成立」整个含在里面。**

**推论 14：「运行时发现」不是洁癖，是升级期的保险 —— 而且它已经被真实兑现过一次。**
Hermes 把内置飞书适配器改成了**插件加载**（模块名从 `plugins.platforms.feishu.adapter`
变成 `hermes_plugins.feishu_platform.adapter`）。我们没改一行、没重装，接管照旧成立，
因为基类是从平台注册表**运行时取**的（`_discover_base_class()`），不是 `import` 写死的。
如果当初抄的是 `from plugins.platforms.feishu.adapter import FeishuAdapter`，
这次上游改动就是一次**静默退回纯文本**（插件加载失败，用户只看到「卡片怎么没了」）。
配套做法：`tests/check_override.py` 用**真加载器**跑一遍并问注册表「现在 feishu 解析到谁」——
这类「上游挪了文件」的改动只有它能第一时间发现。

**推论 15：功能各自有测试 ≠ 用户看到的那条线有测试。**
前面每一节都在验「某一层对不对」（钩子写没写、面板有没有数据、单张卡渲染成什么样），
却**没有任何一条门禁**把「一个回合里用户依次看到的那几张卡」串起来断言过 ——
而那正是 6 项效果的落点。`check_hooks.py` 现在有一节「完整回合的可见帧序列」：
用**真适配器类**（经插件加载器拿到的那个）配一个"录音"客户端，走生产路径
`send_stream_frame` / `interrupt_session_activity`，断言
① seed 帧带等待期占位且 `streaming_mode: true` → ② 正文一开始面板就得在 → ③ 正文到了不许再带占位
→ ④ 收尾帧用 patch、`streaming_mode: false`、**绿边**、不带占位 → ⑤ `/stop` 的载荷里必须有**黄边**。
写这条门禁时踩到两个「验了不存在的场景」的坑，都记在那一节的注释里：核心**自己**会跳过
文本未变的中间帧（所以纯推理阶段没有帧），以及我们自己的 0.25s 节流窗口（不等过它，
中间帧会被跳过、断言只是在读上一帧）。

**推论 16：客户端动画这类「只有眼睛能判」的东西，最终必须由人判 —— 但代理要把判断成本压到一眼。**
打字机到底有没有在逐字，API 永远看不到。我做了能做的一切（字段被接受、帧序列、颜色、载荷、
CardKit 整链 `code=0`、会话开关语义），最后靠**一张公平对照卡**定案：甲（普通卡 + `message.patch`）
与乙（CardKit 实体 + `card_element.content`）**同节奏、同切分**长大，用户一眼就说出
「甲是几个字几个字跳、乙是一个字一个字冒」。反过来我也犯过代价不小的错：**先跑再问** ——
动画是实时行为，跑完再让用户回看等于没问（白等了三轮）。**做法：凡是「必须实时看」的验证，
先让用户在场，再用循环播放把时间窗拉长**（`/tmp/cardkit_loop.py` 每 ~9 秒重来一次，想看多久看多久）。

**推论 17：变异检查器的锚点必须唯一 —— 锚点撞车时它会**替你把结论写反**。**
`tests/mutate_check.py` 用 `text.replace(old, new, 1)` 做定向变异，只换**第一处**。
我新写的一条变异拿 `if panel:` 当锚点，而这段字符串在 `cards.py` 里出现两次
（统一面板那处在前面）⇒ 它改了**无关分支**，然后照常跑四个门禁、照常打印
**🟢 全绿（断言没有判别力！）**。也就是说：报告里的「没有判别力」是假的，
真实情况是「这条变异从未生效」—— 而这两种结论指向完全相反的行动（一个叫我去补断言，
一个叫我去对准锚点）。**规矩：`count(old) != 1` 一律按「锚点有问题」处理、
拒绝下结论、退出码非 0**，与「锚点没找到」同级（对照表也一样）。
推论 6/7/8 说的是「断言没有判别力」，这条说的是**检查器自己**会撒谎 —— 同一类病的第三层。

**推论 18：清点类证据必须先按主键去重，再谈论「多少条」。**
DM 残留盘点脚本没验证 `page_token` 是否真的前进，飞书把**同一页返回了 4 次**，
于是报告写着「最近 3 天共 200 条、已删除 4 条」—— 那 4 条的 `message_id` **完全相同**，
是同一条消息的副本。按 id 去重后真实数字是 **832 条消息 / 182 条未撤回的卡片**，
那一轮实际只删掉 1 条。**凡是「我清掉了 N 条 / 我查了 N 个」这种成果数字，
都要先问一句：这个 N 是按什么去重的？** 没有去重的计数是虚构的，而它会被当成证据写进报告。
同一条纪律也适用于「我审计了 N 个文件」「我跑了 N 个用例」。

**推论 19：断言可能被**更早的另一个失败**顺带满足 —— 它绿，但不是因为被测的那件事。**
（2026-09-13 实测，同一个测试函数里连中两次，两次都表现为「变异全绿」。）

第一形态：**位置**。我给「建实体回 `code=0` 但 `card_id` 是空串 ⇒ 必须 fail-open」加了用例，
放在 ⑤（「拿不到 SDK ⇒ 必须 fail-open」）**后面** —— 而 ⑤ 把 `_ld_ck_requests` 换成了
「没有 SDK」的哑对象。于是那一帧本来就因为**没有 SDK** 返回了 `False`，我的两条断言
（返回 `False`、没发实体卡）全部满足，而「空 card_id 的闸门」根本没被执行到。
修法：把用例移到恢复哑请求对象之后，并**额外断言「被测的那一步真的被调用到了」**
（`calls["create"] == 1`）—— 那一条才是判别力的来源。

第二形态：**路径**。同一轮里，一条变异的锚点串在文件里出现两次（见推论 17），
它改到了另一处代码，于是「变异没生效」被读成「断言没判别力」。

第三形态：**断言观测的是我自己写的替身**。我给「发实体卡必须带 `uuid`（重试去重键）」写了断言，
但它断言的 `uuid` 来自**测试替身**里的 `send_entity` lambda —— 是替身自己填的。于是把生产代码里的
`.uuid(...)` 删掉，替身照样给出 uuid，变异 `CK21` **全绿**。修法：这条断言必须直接打在
**真 SDK 请求对象**上（调生产的 `_ld_ck_requests()` 拿请求；SDK 不在就打印跳过原因，
别让「没跑」被读成「通过」）。同一轮里还有一次「拿到了替身却以为拿到了生产函数」：
用例中途把 `_ld_ck_requests` 换成了替身，我再去 `LarkDeckMixin._ld_ck_requests()` 取到的就是替身
（靠 AttributeError 才暴露）—— **要用开头存下的那个原函数引用**。

三者的共同点：**门禁绿了，但它绿的原因与你要证的那件事无关**。
所以每条新断言都要问一句：**「这条断言为什么会绿？」** —— 如果答案是「因为之前某一步先失败了」，
那它守的不是你以为的东西。变异检查器只能告诉你「撤掉修复它红不红」，
它**不能**告诉你「它绿是因为哪条路径绿」—— 这一层只能靠人想清楚依赖顺序。

**推论 20：门禁的「失败标记」配错时，它自己的判别力会**静默降级** —— 而报告照常打印。**
（2026-09-15 第十二路审计实测。）`tests/mutate_check.py` 给每个门禁配了「失败时会出现什么字串」
的清单，用来区分 `red-assert`（有判别力）与 `red-crash`（只是把代码弄坏了）。
`check_clarify_e2e.py` 那一条被配成了 `"FAIL: "`（带冒号），而那个脚本 `check()` 打的是
**`FAIL  `（两个空格）**、收尾打 `FAILED: N 项 -> …` ⇒ **永远匹配不上**。后果不是假绿
（green 那一侧走的是 `CLARIFY E2E OK` + 退出码，是对的），而是三种更坏的东西：
① 报告里「断言红」那一列对**这个门禁**恒为空 —— 按它归因会一直错；
② 某个变异**只被这个门禁抓住**时，`main()` 会走 `elif not evidence:` ⇒ 退出码 1，
   人会去找一个不存在的问题；
③ 真出事的变异被标成「只有崩溃」，那一行读起来像「你把代码弄坏了」，不像「断言失效」。
**做法：凡是「判 A 还是 B」的判据，都要拿 A 的**真实输出**去校正一次，而不是照抄一个
看起来对的字面量。** 这一条与推论 17（锚点撞车会替你把结论写反）是同一类病的第四层：
推论 6/8 说的是「断言没有判别力」，17 说的是「变异没生效」，20 说的是「分类器看错了」——
三层都会让报告说反话，而三层都只有一个修法：把判据对着**真实输出**实测一遍。

**推论 21：文案是给用户看的逻辑 —— 改文案而不改断言，等于把一条错话锁进测试。**
（2026-09-15，同轮。）R8 的失败 toast 原文是「提交未生效：可能已被处理或过期，**请重试**」，
而它唯一的触发条件（`resolve_gateway_clarify` 返回 `False`）**只有**「entry 不存在 / `Event`
已 set」两种 ⇒ 再点**永远不可能成功**；而它最常见的触发者「一次迟到的重复点击」那一刻卡片
**已经**显示「已确认」⇒ 用户同时看到两条互相矛盾的信息，合理的反应是把答案**用文字再发一遍**
（变成一条新消息，而 agent 早就收到答案了）。原来那条断言是
`toast.content == i18n.t("clarify.toast_failed")` —— 它对**文案内容**一句话都不说，
把「请重试」改回去照样绿。**做法：凡是「文案不该说某件事」这种保证，断言就要写成
「不许含『重试』/`retry`、必须含『无需重复』」，并把判据尽量落到**用户真正会看到的那一层**
（这里最终落在 e2e 里真 SDK 对象序列化出来的线上载荷上）。**只断言「等于某个字面量」的测试，
测的是「我抄了一遍文案」，不是「文案没撒谎」。

**推论 22：构造「不报错但也不该发生」的载荷，才能验「不许做某件事」的纪律。**
（2026-09-15，同轮。）两条「优先级 / 拦截」类纪律当时都零判别力，根因是**载荷压根没走到那条路**：
① 鉴权拦截：用例没装假网关 ⇒ 即使拦截图四行被删，网关调用也会因为 `tools.clarify_gateway`
导不进来而异常 → `committed=False` ⇒ 「什么都没发生」；而且那条断言盯的字段
（`StubAdapter.submitted`）**全仓只有初始化、没有任何写入点**，恒真（推论 8 的老病）。
② 优先级：三条 R8 用例都只造 `commit=True` 的「其他」，于是 `if not committed:` 与
`if is_other:` 的**先后**从来没有被任何载荷区分过。
**做法：要验「A 优先于 B」，就得造一个**同时满足 A 与 B** 的载荷（这里是
`is_other=True` **且** `commit=False`）；要验「拦住了」，就得让**被拦之后那条路**真的会留下
可观测的痕迹（这里是「提交被发起时记一条」的记录点）—— 一个**不会记录**的观测点
与「一切正常」长得一模一样。

**推论 23：功能级断言要问一句「**默认配置走的是哪条路**」。**
R9 的账本有 7 个记账点，而单测把传输**显式钉成 `patch`**（这是好习惯：用例必须声明自己在测哪条），
于是**默认传输 `cardkit`** 的 seed 建实体与每帧元素写两处**一个断言都没有** ——
把它们换成 `pass`，四个门禁全绿，而默认配置下 `/larkdeck status` 会永远说
「最近写卡：无记录 · 累计 0 次」，用户眼前却躺着一张逐字卡片（第十路审计实测）。
**做法**：① 默认值本身就是一条要被门禁覆盖的路径（本项目已经有一条
`test_declared_defaults_are_an_explicit_decision` 钉「默认值是什么」，但那只钉了声明）；
② 每条「记账/上报」类功能都要在**默认配置**下端到端跑一遍，并把期望值**写死成数字**
（`len(...)+2` 这种由被测代码推出的期望值是自证的：变异把记账撤掉，期望值跟着掉）；
③ 断言要**逐段**钉（seed 后 =1、四帧后 =5、收尾后 =6），否则「漏掉中间某一笔」会被总量掩盖。

**推论 24：心跳/探针这类「诊断信号」不许排在**别人的代码之后**。**
R9 的 `note_inbound()` 曾经是 `_on_pre_gateway_dispatch` 里同一个 `try` 块的**最后一条语句**，
前面还有 `_compat.lookup_session_id` 与 `_panel.bind_chat_session`（另外两个模块）。
任何一个抛异常，`except Exception` 就把心跳一起吞掉 —— 而心跳正是判「消息到没到插件」
的唯一凭据，于是那一次归因**指错方向**（README 当时写着「心跳不动 ⇒ 消息根本没到插件」）。
**做法**：诊断信号放在回调的**第一条语句**（位置本身就是纪律，别靠「记得把别的逻辑放在后面」
这种约定）；给「它前面那句抛异常」写一条用例；顺带把归因写成**可判定**的版本
（一串「或」的情形）而不是一句自信的因果。

**推论 25：口径说明是**承诺的一部分**，不是注释。**
同一批账本里三件事都没写：① 「写卡次数」实为「有写出过东西的**帧数**」（cardkit 一帧最多
3 次逻辑写、seed 是 2 次网络调用、一次逻辑写撞限流最多 4 次 HTTP，全都只 +1）；
② 它是**进程级全局**、多会话并发时显示的是**别的会话**的数字（页脚那条同类说明早就写了，
账本这条一个字都没有）；③ 「写卡失败」不等于「核心收到过几个 `False`」（后者含「没有活跃流
可收尾 ⇒ 按契约交还控制权」这种正常返回）。用户会按字面意思读这些数字 ——
**数字旁边没有口径，等于承诺了一个不成立的语义**。做法：定义写进调用点的 docstring
**和**用户看得见的文案**和** README/AGENTS 三处，并让门禁断言文案本身（本项目已有一条
断言落在卡片的**文本**上，而不是落在 i18n 表上 —— 写在表里但没拼进卡等于没说）。

**推论 26：三方合并会**静默复活**已经删掉的代码 —— 合并之后必须重跑全量变异。**
收尾阶段我把一条「恒假门禁」（死代码，`_card_body_bytes(visible) > 硬上限` 在 R4 之后永远为假）
删掉，并把它对应的变异 `CK23` 改瞄到真正该守的早返回上；随后用 `git apply --3way` 打一个基于
**删除前**那一版的补丁。冲突区在 3-way 眼里是「他们那边有、你这边没有」⇒ 它**取了他们的版本**，
把死代码**还原回来**，而 `git apply` 照常打印成功。症状是最阴的一种：**四门禁全绿、
变异却从红变 🟢** —— 因为变异现在撤掉的那段代码本来就不生效。
**做法**：① 任何 merge / rebase / `--3way` 之后**重跑全量变异**（不是 `-k` 跑一部分），
并**逐个**看还有没有从红变绿的；② 改动「删除」类补丁前先 `git diff <基线> HEAD -- <文件>`
确认没有别的回退被一起带进来；③ 把「合并后必须重跑变异」写进 `AGENTS.md` 的验证节 ——
它不属于「记得就好」的范畴，属于流程硬约束。

**推论 27：方案「做多大」要在审计之后重新拍板 —— 别照着最初调研的措辞做到底。**
R3 最初的写法是「面板里每个工具一行 = 一个元素」，来源是调研里那句「多元素 / 每工具一行 / 批次」。
三路方案审计（预算算术 / 代码吻合度 / 门禁判别力）算完账之后，**收益侧**只有「行级 vs 块级重绘差」，
而**代价侧**是：滑窗写入率从 8.2/s 涨到 10–14/s（零余量）、`300315` 一名两义、
失败分支的白名单合并会把创建记账丢掉（⇒ 重复 id）、切卡要重置 8 个状态键、
以及最要紧的一条 —— **当时的门禁对这条路径零判别力**（golden 夹具与真机场景都没有工具步）。
**做法**：把方案拆成「拿收益的最小形态」（面板拆成推理块 + 工具块，两块都在建实体时定死、
逻辑写不增加）先落地，把「每行一元素」连同它的三件前置（滑窗写入守卫 / `300315` 内层码解析 /
失败分支记账合并）显式写成未开始 + 前置条件。**「推迟」必须带上前置清单**，否则下一个人会以为
它只是没排上期。

**推论 28：改夹具/期望值之后必须**逐字段读 diff** —— 门禁全绿不代表期望值是对的。**
我扩 golden 场景时把工具事件的 `turn_id` 传错（`record_reasoning` 用的是 `(session, turn)` 两个
位置参数，我第二个传成了另一个值），`_touch_locked` 判成「换了回合」⇒ **清空推理轮**，
于是夹具里 `panel_body` 被写成空、只有 `panel_tools` 有内容。**四门禁全绿**，
是我**读夹具 diff** 时看出「这里怎么会是空格」才发现的。
**做法**：夹具/期望值类改动，改完必须把 diff 的**每个字段**读一遍（不是看「测试过了」）；
真机探针的结论也一样 —— 它是给人看的，不看就等于没跑。
另附一条同源教训：断言的**稳定性**也是正确性的一部分。同一个用例在**冻结时钟**与真实时钟下
会得到不同结果（推理轮收尾时标题补 `· 0.0s`，耗时是墙钟算的）—— 我实测到「快时只写工具块、
慢时两块都写」两种结论。涉及时间派生值的场景**必须冻结时钟**（`_STREAM_MIN_INTERVAL` 同时置 0）。
**2026-09-15 又踩到同一条的第三种形态**（R11-B1 的滑窗写入守卫）：守卫的判据是**墙钟**
（1 秒内 ≤10 次逻辑写），而单测为了跑得快把帧间隔置 0、或者干脆把 `time.monotonic` 冻成常量
⇒ 连续帧全落进同一个 1 秒窗口，守卫**正确地**让出装饰 —— 于是「第 2 次写的是哪个元素」这类
断言随机器快慢漂移。处置不是改判据，而是**把守卫本身在单测里冻住/构造**：一条用例把窗口
**显式塞满**来验两条边界，另一条用**按 0.25s 前进的假时钟**验「稳态不该触发」。
**凡是新加「按时间」的判据，先问一句：它会不会跑到既有断言的时间线里去。**

**推论 29：探针发出去的东西必须「每条都可定位」—— uuid 唯一 + 记账不漏。**
两条都是 2026-09-14 实测踩出来的：① 澄清探针用**固定 uuid**，我删掉那张卡后用同一个 uuid
重发 ⇒ 飞书按 uuid 去重，回**同一个已删的 `message_id`**、`code=0`，而用户 DM 里**什么都没有**
（我却让用户去找一个不存在的卡）；② `--cardkit-prod` 那一路建卡后**没记 `message_id`** ⇒
`--clean-only` 按账本删时删不掉它，DM 里留了一张「认不出来的探针卡」，只能靠人长按删。
**做法**：探针每次发消息的 uuid 里带时间戳；**建卡/发卡之后立刻把 id 写进账本**（同一进程内
`_save_sent_ids`）；清理只按账本或**已知 card_id**（`cardkit.v1.card.id_convert(message_id)`
能把 message_id 映射回 card_id，用它把「认不出来的卡」比对出来 —— 但不能靠时间窗猜）。

**推论 30：官方扩展点「存在」不等于「被调用」—— 上手前先 grep 它的调用点。**
2026-09-14 实测：`AGENTS.md` / `README` 一直写着「我们覆盖 `format_tool_event` 返回 `None`
来吃掉核心并进正文的工具行」，配置键 `progress_lines_in_body` 也照这个实现。结果是
**它一直是空转的** —— `format_tool_event` 的唯一调用点在 `gateway/stream_dispatch.py`，
而那个 `GatewayEventDispatcher` **只在测试里被构造**（全树 grep：生产侧零引用）；
真机上的工具行由 `gateway/run_turn_runner.py` 生成、被 `gateway/stream_consumer.py`
合成进同一帧，走的是另一条路。用户看得见的症状（正文里混着 `⚙️ terminal: "…"`）因此
**与文档说的机制完全无关**，而我照文档查了两轮都没解释清。
**做法**：把「覆盖某个方法」当成修复手段之前，先 `grep -rn "<方法名>" <核心源码>` 找到
**调用点**，并确认那个调用点在**生产路径**上（而不是只在 `tests/` 里被构造的类）。
签名存在只证明「契约还在」，不证明「它会被调到」。

**推论 31：判据要能被**证明**，不能只是「长得像」—— 形状可以被别的来源伪造。**
同一个功能的两次实现对照得很清楚：旧版（`8f81b4d` 移除）用裸分隔符 `"\n\n---\n"` 当**切点**，
而 `---` 本来是普通 markdown、模型随时会写 ⇒ 误判一次就把整条回答切成半截，而核心对
finalize 是**乐观记账**、不会再补发（答案彻底消失、任何一层都不报错）。
R11-A7 把同一份信息改成**验证条件**：我们自己通过公开钩子攒一份正文增量，
`帧文本 == 我们的累积 + 分隔符 + 尾巴` ⇒ 那条尾巴**只可能**是核心加的
（模型写下的每个字节，含它自己写的 `---`，都在累积里）。
**做法**：判据里出现的每一个「形状」都问一句「这个形状能不能由别的来源产生」；
能，就不是证明、而是猜。**再加一条**：证明不了时必须**原样放行**
（退化成旧行为），而不是**猜一个**。

**推论 32：把状态「搬进共享容器」时，**锁、在飞集合、结论性缓存要一起清点**。**
2026-09-14 实测（R11-A0）：真机根因逼我们把模块状态搬到进程级共享盒子，第一批只搬了容器，
漏了三类，每一类的症状都不一样、而且都不像「共享没做全」：
① **锁**没搬 ⇒ 两份模块对象各持一把锁 ⇒ 互斥从构造上失效（一份遍历会话表、另一份插新桶
   ⇒ `RuntimeError: dictionary changed size during iteration`，表现为**偶发丢面板**）；
② **在飞集合**（`_INFLIGHT`）没搬 ⇒ 另一份 `discard` 不掉 ⇒ 那个模型**永远不再被探测**
   （静默退化成家庭兜底，页脚显示一个错的上下文窗口）；
③ **结论性数据**（钩子挂载数 / 命令注册）没搬 ⇒ 同一个自检按「读到哪一代」给两个答案。
**做法**：搬完容器之后，逐个问三句 ——「谁在守着它」（锁同源吗）、「谁在别处也持有一份」
（在飞/去重/限流这类跨调用的小集合）、「它答的是数据还是结论」（结论必须唯一）。
同时把**键清单收敛到一处**并加断言（`set(真实盒子) == set(声明)`）：两处各声明一串同名键时，
加一个键很容易只加一处，漏掉的那份会**静默新建一个不属于盒子的容器** —— 症状与「裂脑」一样。
⚠️ 反向纪律同样重要：**不是所有东西都该共享**，共享「代码」（比如类缓存）会把活对象冻在
上一世代的代码上。所以清点表里要有一条「**明确不共享 + 理由**」，而不是只列「已共享」的。



## 三、五个验证盲区

- **`install.sh --copy` 的 `FILES` 数组是手写的。** 新增模块漏同步会装出一个「少了指标采集
  和钩子订阅」的插件 —— 而**默认软链模式永远测不出来**，只有 NAS 会中招。
- **配置键有两处真相**：文档写的路径、代码真正读取的路径。曾经文档写
  `plugins.larkdeck.*`，代码里却没有任何读取路径，静默空转。`check_override.py`
  目前是唯一端到端断言这件事的地方。
- **检查脚本自己补的字段，会盖住生产路径上的丢字段。** `check_hooks.py` 走的是真派发器，
  但载荷是**脚本自己构造**的（`base_url=...` 是它写进去的）—— 于是「回调把载荷字段丢了」
  这一跳它看不见：2026-09-14 页脚恒显示 `ctx x/128k`（DeepSeek V4.1 Flash 真实 1M），
  而四门禁当时全绿。判据必须落在**真回调**上：`test_units.py::test_api_hook_passes_base_url_to_the_context_probe`
  直调 `hooks._on_api_request` + 打桩上游 API，断言**到达 `get_model_context_length` 的参数**；
  变异清单 `HK` 锁它（撤掉透传即红）。规矩：**门禁比生产多给的字段，就是门禁比生产少看的字段。**
- **`--preflight` 只回答「锚点还在不在、唯不唯一」，不是提交前的绿灯。**（2026-09-16 实测。）
  把 `core/i18n.py` 弄成语法错误，它照样 **318/318 ✅、exit 0**，而全量跑立刻
  `EXIT=2`「基线不是绿的」—— 因为**预检不跑门禁、也不做基线自校验**。它看不出：
  锚点落在注释里、落在用例**不经过**的分支上（推论 35）、或撤掉后**压根不会变红**。
  它的定位是**前置筛子**（0.1 秒，改完锚点先用它，别等 65 分钟的全量）＋ `-k` 子集跑的补盲
  （它有意**不受 `-k` 影响**，所以子集跑看不见的坏锚点它照样查）。
  **把「预检 ✅」当绿灯 = 把「我查了门牌号」当「我进过这间屋」。**
- **用例里的无界等待，会把「断言真的抓住了变异」伪装成 💥「没有证据」。**（2026-09-21
  收口复核实测。）`V1-2` 短路 `panel partial` 分支后，定向用例 0.4s 断言红，但**整支**
  `test_units` 挂 >60s ⇒ 45s 门禁超时 ⇒ `mutate_check` 记 💥（不算判别力证据）——
  清单里于是出现一条**有牙却被记成没牙**的变异（历史上靠一条手写的 `--only` note 续命）。
  根因是测试自己的 `await started.wait()` **无界**：被测分支不再发那笔写，事件永远不 set。
  ⇒ 测试里的等待一律**有界**（本项目 `_await_event`：`asyncio.wait_for` + 超时转
  `AssertionError`）；判据是「这条用例挂多久都不该超过门禁超时预算」。
  **同一条纪律也适用于生产代码**（禁 sleep、等待必须有界）——只是这次踩的是测试侧。

## 四、交付约定（此前只活在 commit message 里）

每个 commit 的 message 末尾附一行**实测**门禁结果（数字照抄当次输出，别沿用旧值）：

```
测试：120/120 · OVERRIDE OK · HOOKS OK · CLARIFY E2E OK · 变异 38/38 全红（+1 条对照预期绿）
```

改过卡片结构就再加 `probe_render 真机 N 卡 code=0`；改了断言就必须带**变异结果**
（`mutate_check.py` 的「N/N 全红」），否则「断言有没有判别力」这件事没有任何证据。
只写跑过的；没跑就写没跑。

**不让用户做我能自己做的取证**（用户的规矩，2026-09-15 原话：「不要让我反复复现/验证，
能自己取证的自己取」）。能自己读的日志、能自己数的帧、能自己发的探针，一律自己取；
只把**物理上只有人能做**的那一步交给用户（例：真机点一次按钮、看一眼动画），
并且**事前**把读数与判定协议备好 —— 探针 ⑮ 的点击前读数就是这么取的：
平台 `connected`（2026-09-15T11:03:08Z 更新）、`agent.log` 3.82 MB（未到 5 MB 轮转阈值）、
WS 有过 19 分钟空档（`18:43:54→19:03:08`）⇒ 那一次点击的结论才是**可判的**，
而不是把「没看到日志」的三种含义（没投递 / 网关离线 / 客户端没渲染）混在一起问人。
配套：**用户的每一次操作都要给编号步骤 + 期望现象**，别让他在叙述里找动作。

**`mutate_check.py` 退出码非 0 有两种，都算红。** ① 变异跑完但门禁没抓住（断言假绿）；
② **锚点失效**（输出里的 `❓ 锚点没找到` —— 源码改了、清单里那条变异的原文串已不存在）。
第 ② 种**不是**「少验一条」，而是「清单与源码脱节」：跑不到的变异等于没验，
必须把锚点重新对准当前源码、重跑一遍，**不许把「跑不到」当「通过」**
（2026-09-13 真实发生：`_print_frequency_ms()` 重构成 `_log_print_ms_once()` 之后，
两条 P2 变异的原文串再也匹配不上，而基线仍然是全绿）。
③ 还有第三种**看起来是红、其实不是**：报告写 `🟢 全绿（断言没有判别力！）`，而真相是
「变异没生效」—— 判据是 `count(old) != 1`（锚点歧义）或锚点没找到，**两者都拒绝下结论**
（见推论 17）。
④ 分类器那边还有一种：真断言失败被算成 `red-crash`（`_FAIL_MARKERS` 与门禁真实输出不符，
见推论 20）—— 它不改退出码，但会让「断言红」那一列**恒空**，据此归因必错。
所以**改 `mutate_check.py` 之后，除了跑变异，还要拿一份「已知会红的门禁输出」核一次
`_classify` 的判定**。

**推论 33：门禁要先自证「测的就是这份代码」——「同名拷贝」也能造成二类假绿。**
这是 R11-B2 的对抗审计实测出来的（我自己在起临时拷贝时也当场踩到）：`tests/*.py` 靠
`sys.path` 找 `larkdeck`，而它们把「脚本父目录的父目录」插到 `sys.path[0]`。只要搜索路径上
更靠前的地方有**另一份同名目录**（`/tmp` 下前一次导出的镜像、旧拷贝、陈旧的 `__pycache__`），
门禁就会去测**那份**代码 —— 审计实测：把 `capacity_exceeded()` 整条改坏（内层码解析全灭），
在镜像目录里跑出 **184/184 全绿**；唯一翻红的只有变异验证器的锚点自查。
**这与「`mutate_check` 的快照目录必须叫 `larkdeck`」是同一种病的两个入口**：门禁跑了、
断言也真的跑了，只是**跑的不是这份代码**。而它比「锚点失效」更隐蔽 —— 后者至少会报一句。
**做法**：门禁开跑时比对**被测模块的真实路径**是否在本仓库目录内（`test_units.py` 顶部那条
`_gate_import_problems(...)` + `SystemExit`），并且**给这条守卫本身写一条用例**（拿一个外来
路径问它，它必须报问题）—— 否则那只是一句注释（推论 11：给验证器自己写输入）。
**移进副本、换目录、并行实验之前**，先确认这行自证没有把副本误判成仓库（副本也要能跑）。

**推论 34：「撤掉修复也不红」的**形态清单** —— 先按这张表分类，再动手修。**

本项目的头号缺陷类型是**门禁绿了、但它绿的原因与你要证的那件事无关**。这一族到 2026-09-16
登记了 **8 种形态**，症状全都一样：变异打了上去（锚点也对），四门禁全绿。
⚠️ **编号是清单序号，不是发现顺序** —— 以前 `AGENTS.md` 用「第五种形态」指代最后一条、
并把前四种写成「推论 6/7/8」：**三个编号对四种形态**，一个对不上的引用本身就是这一族的病
（2026-09-16 收口到本表，别再在别处重新编号）。

| # | 形态 | 病根 | 首次实测 |
|---|------|------|----------|
| ① | 断言**结构上不可能失败**（假实现永不抛异常） | 断言 | 推论 6① |
| ② | 夹具用**默认值**去测，而变异改的是「把自定义值传下去」那一跳 | 断言 | 推论 6② |
| ③ | 断言**看不见被保护的那一层**（`_positive` 的 nan/inf） | 断言 | 推论 6③ |
| ④ | 「**空集 / 空列表 = 一切正常**」 | 断言 | 推论 8 |
| ⑤ | 断言被**更早的另一个失败**顺带满足（位置 / 路径 / 替身三形态） | 断言 | 推论 19 |
| ⑥ | 「修复」本身是**死代码**（被同文件后面的旧赋值覆盖） | **修复没生效** | 推论 7 |
| ⑦ | **输入构造让错误分支不可达** | 断言 | `G1-22`，2026-09-15 |
| ⑧ | 判据读的是**初始化早就跑完**的那一格 | 断言 | `X20`，2026-09-16 |

⑦ 的现场：用例想证明「条件③是**前缀**判据、不是**子串**判据」，探针文本写成
`"宋" + 累积 + 分隔符 + 进度` —— 看着对，但条件④按**长度**切片（`text[len(accumulated):]`），
多出来的那个字符让切片**错位** ⇒ 尾巴不以分隔符开头 ⇒ **连错误实现也原样返回**；
把 `startswith` 放宽成 `not in`，四门禁全绿。⑧ 的现场：判据直接读「已经建好的那个账本格子」，
而初始化分支在**进程启动时**就跑完了 ⇒ 撤掉那行初始化代码，格子照样是满的
（必须先把它删掉、逼初始化再跑一次）。

**做法**：用例必须能证明**「错误实现会走进那条分支」**；拿不准就把这条自证也写成断言
（`G1-22` 就是这么做的：先断言**构造本身**能把错误实现推到剥离分支，再断言行为）。
⚠️ 附则（同轮实测）：**关键性质必须单独成条** —— 同一条判据放在大用例里时，任何相关变异都先
触发前面的具体断言，这条**从不触发**，「它有没有判别力」就永远无法证明（实测：独立成条后
同一个变异让 `198/199` 变成 `198/200`）。

**推论 35：锚点「唯一」还不够 —— 它必须落在**这批用例真的会经过**的语句上。**

2026-09-15 实测（`G2-11`）：锚点 `if self._ld_transport() == "cardkit":` 在源码里**恰好唯一**，
`count(old) != 1` 那道闸门放行；但它在 `state is None` 的非 finalize 支上，而对应用例喂的是
`finalize=True` ⇒ 在更早的 `if finalize: return False` 就返回了 ⇒ **变异插进去的那句从来没被
执行过**，报告照常打出 🟢「断言没有判别力」，结论正好写反。
**做法**：改完锚点必须用 `-k` **逐条重跑**，而且**只认 `🔴 断言失败`** ——
`❓ 锚点没找到`（清单与源码脱节）与 `💥 只有崩溃`（把代码弄坏了）**都不算判别力证据**。
⚠️ `--preflight` 也看不见这条：它**只数锚点出现几次**，不跑门禁、不看控制流。
这一条与推论 17（锚点撞车）、20（分类器看错）同属「**报告说反话**」一族，但入口不同：
17 是**找错了地方**，20 是**看错了结果**，这条是**找对了地方、但那句话没被执行**。

**推论 36：写「已修」之前先证明缺陷存在 —— 否则你会修一个不存在的缺陷，并给它配一条无牙的用例。**

2026-09-16 实测（本批次最贵的一条）。CHANGELOG 当时写着「**建实体时页脚元素不进卡**（审计实测的
功能缺陷）…已改成按配置决定」。**那个缺陷不存在**：`_ld_ck_create` 建卡用的是函数体里**写死**的
`footer_text=("" if _cfg("footer") else None)`（本来就按**配置**判），调用方传进去的同名**形参
从来没被读过**（AST 实测「形参未被使用」），而那一行在 `v0.4.0`、父提交与当时 HEAD
**三处逐字节相同**。⇒ 那次「修复」是空转：删掉一个**没有任何行为影响**的形参（连带它唯一的生产者
`_ld_seed_footer_text()`，全仓零调用点），并为它写了一条用例 —— 而那条用例恰好是本批次自己
点名要消灭的两种无牙形态（**只调 helper = 验函数不验接线** ＋ **手工照生产那一行再建一次卡 =
验表达式不验调用点**）。
**做法**：① 写下「已修」之前先写出**可复现的缺陷现场**（哪一行、什么输入、什么症状），
写不出来就说明缺陷不存在；② 「这个参数/字段没人读」这类结论用 **AST 或 `grep` 数一遍**，
别用「看起来应该在读」；③ 生产代码与它的判据**同一次**引入时，先问「**撤掉生产代码那一行，
判据会红吗**」—— `G2-9` 就是这么重新对准的（实测必红）。

**推论 37：注释里的「为什么」必须是**推导**，不能是同义反复；外部前提要有**独立**判据。**

2026-09-16 第四轮审计实测：`_strip_core_progress` 的 docstring 把「只剥后缀」归因于
「因为我们只做后缀剥离」—— 那是**同义反复**，不是保证。真正的保证来自条件 ③+④ 的**推导**
（`tail = text[len(acc):]` 且 `tail.startswith(SEP)` ⇒ `acc == text[:text.index(SEP)]`
⇒ 必然是前缀），而那条推导又依赖一个**外部前提**：**我们的正文累积与核心的累积逐字节同源**
（`agent/stream_delivery.py:314` 把同一个 `text` 既投给钩子又累加）。前提一变，
`display` 就可能不再是帧文本的前缀 ⇒ 在**切卡接缝**上静默吞正文，而四门禁全绿。
**做法**：① 写「为什么」时问一句「这是**推导**还是**同义反复**」——同义反复就删掉，改写成真正的理由；
② 凡是**外部前提**（依赖核心行为、依赖另一个模块的同源性），要有一条**独立**用例钉住它，
且那条用例要能**证明自己不是恒真的**（带构造自证，见推论 34）。
⚠️ **第 ② 条已兑现（2026-09-16 补）**：那个「同源」前提**现在有判据了** ——
`tests/check_hooks.py` 的**前提核对**那一格**驱动核心真实的投递链路**：
`StreamDeliveryMixin._fire_stream_delta` →（核心 docstring 写明的接线）`consumer.on_delta`
→ `_drain_queue` → `_filter_and_accumulate` → `_append_accumulated`，而**同一行代码**把
**同一个 text** 交给 `_enqueue_stream_hook`（我们收到的就是它）⇒ 断言两边**逐字节相同**；
再拿核心真实的 `_compose_frame_content()` 合成一帧喂给我们真实的 `_strip_core_progress`，
断言剥回来的正是核心自己的正文。变异 `PA-1`（把我们的入账改成 `.strip()`）实测**必红** ——
它吃的正是核心在工具轮边界自己插的那个 `"\n\n"`。
**桩掉三处，都在代码里写明**：异步 `run()` 循环（同步泵一次队列）、工具轮边界那个布尔位、
以及宿主侧 `_strip_think_blocks`（identity —— 核心真实现会改写文本，但 `stream_delivery.py`
是**洗完之后**才把同一个局部 `text` 既给回调又给钩子 ⇒ 只改输入形状，不动「同源」这个结论）。
⚠️ **归属必须确定性**：这一格最初用 `answer_state("")` 读，走的是进程级「最近活跃」指针 ——
2026-09-16 对抗审计实测：把正文仓库的**按会话分桶整条拆掉**（`_answer_bucket_locked` 的
`sid` 换成常量），这一格**照样绿**。修法是先 `bind_chat_session(chat, session)`
（真机上由 `pre_gateway_dispatch` 绑定）再按 chat 读，并自证归属落在目标会话上；
变异 `PA-2` 钉这一条。⚠️ 同一轮审计还实测出：**上游改名时它会抛 `AttributeError`**，
只打 traceback、没有 FAIL 行，而且**这一格之后的断言全部不再执行** ⇒ 整段驱动已套上
try/except，退化成一条可读的 FAIL（实测：注入模拟故障 ⇒ `EXIT=7` + 一行 FAIL，
后面「黄金序列 ①..⑤」照常跑完）。
⚠️ **仍未覆盖的（如实登记）**：① `run()` 自己的分支（含 `_clean_for_display` 等显示前加工）

⇒ 不剥 ⇒ 只是进度行可见），不是吞正文。登记在 `docs/plan-v1.md` 附录 F。

**推论 38：结论要标**证据强度**；「官方文档写了」不等于「真机验过」，别人的代码注释不算证据。**

两个现场，同一格（2.0 `button`）：
① **2026-09-12 更正**：旧结论「2.0 的 `behaviors` 回调到不了服务端」的论据是**第三方插件的
代码注释**（而那个插件自己的代码还与那句注释相矛盾）。真机事实是「2.0 卡里放 1.0 的 `action`
行会被飞书拒 `230099`」—— 论据**抄错了对象**，于是整条结论错了两天。
② **本批次的处置**：`select_static` / `multi_select_static` / `input` 三格**真机点过**
（探针 ⑫⑬⑭ 的「探针点击到达」日志 + `check_clarify_e2e.py` 全绿），而 `button` 这一格
**只有官方文档** ⇒ `AGENTS.md` 与文档的措辞按证据强度**降级**（不许写成「已验证」），
并留一个**只花用户一次点击**的探针 ⑮ 去补这一格。
**做法**：① 每条结论都要答得出「这是**谁**量的、**怎么**量的」；答不出就降级措辞
（「文档已证」≠「真机已证」≠「我们验过」）；② **只消耗用户一次**的实验，事前把**判定协议**
写下来（成立 / 不成立 / **不可判定**三态，见 `docs/handoff-route.md` §12），事后照条款判 ——
否则「没观察到」会被顺口解释成「不成立」，而真相常常是**这次没做成**
（探针没发出去 / 网关离线 / 客户端没渲染）。

**只报实测结论**：门禁数字、变异测试矩阵（「把修复回退就变红」）、真机返回码。
描述性总结（「应该没问题」「逻辑上是通的」）不算结案证据。
