## 二、这个项目的头号失败模式是「静默」

不报错的失败比报错的失败贵得多。已经踩过的静默坑：

- **按钮点了没反应** —— 1.0 的 `action` 容器混进 2.0 卡，飞书拒收但不报错；
- **折叠面板退化成普通行** —— `header.title` 塞了 `lark_md`，或者没给 `icon`
  （没有 icon 就没有展开控件，面板变成一个永远打不开的抽屉）；
- **配置写了不生效** —— 键路径写错就等于没有读取路径，YAML 全部空转；
- **钩子没挂上** —— 只是页脚少两段、面板空着，卡片照常渲染，从表面看不出来；
- **每一帧卡片更新都失败** —— `message.update` 拒收 `interactive`，而失败会**回落**成内置
  文本编辑：消息照样发出去，只在 WARNING 级留一行，很容易以为一切正常；
- **面板永久不渲染**（2026-09-12 实际踩过并回退）—— 曾想用 `turn_id` 把卡片和会话精确对上，
  但两侧的 `turn_id` 是**两个不相干的命名空间**：钩子载荷给的是 agent 的
  `_current_turn_id`，而 `send_stream_frame()` 收到的是 stream consumer 现生成的裸
  `uuid4()`。join 永远匹配不上，面板直接消失，**且不报任何错**。
  代码里的警告块见 `core/panel.py::snapshot`。
- **整条回答被渲染成一个空格**（2026-09-12 实际踩过并移除该特性）—— 「叙述归档」用裸分隔符
  `"\n\n---\n"` 猜核心有没有往帧里拼工具进度块。但核心的合成式是
  `"\n\n---\n".join(p for p in (accumulated, progress) if p)`：**没有工具进度时帧文本就是
  累积正文本身**。而 `---` 独占行正是普通 markdown 分隔线，模型随时会写。一旦误判，
  归档点被推到分隔线处 → 之后每帧都算不出正文 → 卡片被刷空 → finalize 的
  `display or " "` 让答案只剩一个空格。**而核心按完整帧文本乐观记账、判定「已送达」，
  不会再补发** —— 答案彻底消失，任何一层都不报错。
  教训：**当一段文本既可能是「系统生成的元数据」又可能是「用户内容」时，不要用字符串
  匹配去猜**；判错两个方向都会吞内容，那就选不猜。详见 `core/adapter.py` 顶部说明。
- **卡片在真机上根本发不出去，本地门禁全绿**（2026-09-13 实际踩过）—— 2.0 的
  `card(title=...)` 把 `i18n_text()` 返回的**节点**直接塞进 `plain_text.content`，产出
  `{"content": {"tag": "plain_text", ...}}` 这种嵌套结构；飞书整张卡拒收
  （`230099 / ErrCode 200621 parse card json err`）。1.0 的 `legacy_card` 一直处理正确，
  所以**只有走 2.0 的澄清卡**中招 —— 而它们本地单测只核「有没有 header」，完全看不出来。
  教训：**能被本地规则判定的卡片合法性，就该在本地钉住**（现在是
  `test_every_text_node_carries_a_string_not_a_nested_node`：所有文本节点的 `content`
  与 `i18n_content` 的值必须是字符串）；真机探针留给「只有 API 能裁决」的那部分
  （枚举值、元素上限、方言接受度）。
- **探针永远说「不支持」**（2026-09-12 实际踩过）—— 转发 `metadata` 给父类时写成
  `getattr(type(parent), "interrupt_session_activity", None)`，而 `parent` 是
  `super()` 对象、**`type(parent)` 恒为 `super`** ⇒ 探针拿不到方法、永远判 False，
  参数被静默丢掉。`super()` 对象要用 `getattr(parent, name)`（会沿 MRO 找到下一个实现）。
  同类：任何「探测函数签名」的代码，先确认你探的是**函数本身**而不是包装物。
- **门禁只核「字面形状」，从不走真实判据**（2026-09-13）—— 2.0 多选答案的断言原来是
  `json.loads(answer) == [...]`，于是「把答案改成根本不可能被接受的形态」照样全绿，
  而真机上用户「选完没反应」。同类还有：只断言「卡里出现过 behaviors 字样」，于是
  「少给一个组件挂 behaviors」也全绿。做法：**断言要走下游真正消费它的那个解码器**
  （`check_clarify_e2e.py` 现在直接调 `tools.clarify_tool._clean_answer` 验答案）。
- **门禁漏掉整条关键线路**（2026-09-12，变异测试查出来的）—— 把 `hooks.py` 里
  `kind == "text"` 那个分支整条删掉（于是「正文切断推理轮」永久失效、推理连成一个
  巨大的「第 1 轮」），**四个门禁全部照绿**。同一批还有 `adapter.py` 不传 `rounds=`、
  把 `panel_expanded` 写死 False —— 都没有任何断言。做法：每加一个特性，先把它**关键
  信号**那一行改坏，看门禁是否变红；不变红就补断言。

**推论 1：每加一层能力，都要顺手给它配一个「能自证」的东西。** 要么是门禁里的一条断言，
要么是限流的诊断日志（现有例子：`面板无数据` / `pre_tool_call 钩子触达` / `指标已接入`）。
不要拿「看起来是好的」结案。

**推论 2：跨层的「同名字段」必须先证明同源，再假设相等。** 上面那个 bug 的测试之所以
全绿，是因为测试里两边喂的是我自己传的同一个值 —— **测试把我的错误假设一起编码进去了**，
这叫自证循环。验证跨层契约只能去读**真实源码**里的取值点，或者写走真派发器的集成测试
（`check_hooks.py` 就是干这个的）。

**推论 4：同一条业务规则在两条路径上可能有相反的结论 —— 别把 A 路的实测当成 B 路的。**
2026-09-13 实证：多选答案的形态，**文字回答**那条路径（`clarify_gateway`）会把 JSON 数组串
判成「无效选择」，而**卡片点击**那条路径（`resolve_gateway_clarify` → 工具侧
`_parse_multi_select_response`）对 JSON 与逗号串**都能解码**。审计报告里「JSON 一律被拒」
是 A 路的结论，差点让我把 B 路改坏。凡「某格式不被接受」的结论，都要问一句
**在哪条路径上、谁在解析**。

**推论 6：断言要看**判别力**，不是「有没有断言」。** 2026-09-13 连续三轮审计各戳穿一条：
① 「父类不许被调用两次」那条断言里的假父类**永不抛异常**，而「双跑」只在父类**内部**抛时发生
—— 这条断言结构上不可能失败；② 「over-budget 档也要带打字机」我第一版用**默认值**去测，
而变异是「忘了把自定义参数传下去」⇒ 默认值恰好等于期望值，照样绿；
③ 第六轮我**自称**修好的 M22（`_positive` 的 nan/inf 保护），第七轮实测**仍然全绿** ——
那条「遍历坏值」的断言根本看不见 `_positive`（`nan` 走 `_positive→False` ⇒ 卡片里没有这个
字段 ⇒ `continue`；`inf` 走 `True` ⇒ 由 `streaming_config` 自己的 `try/except` 接住）。
**做法：补完断言先问一句「我要防的那个改动，是这一行能看见的吗」**，
再用变异实测一遍；看不见就换观测量（传自定义值 / 让假实现真的抛 / 直接打被保护的那一层）。
更不能把「已修」写进注释和文档 —— 那会让下一个人不再检查（本轮就发生了）。

**推论 7（第七轮阻断项）：改常量的「口径」时，必须 grep 出所有同名赋值，且回归 fixture 要贴着新阈值写。**
`_MAX_TRACKED_TEXT` 从 20000 字符改成 120000 字节时，文件里**旧的**
`_MAX_TRACKED_TEXT = _cards.CARD_BYTE_BUDGET`（40000）没删 ⇒ Python 后赋值覆盖前者 ⇒
整个修复是**死代码**，而那条回归用例的 fixture 恰好卡在 40000 上，**它的绿正是来自这句覆盖**
（删掉覆盖行，测试立刻变红）。两条制度性做法：① 形状断言 —— 现在有一条「阈值 + 卡片固定开销
≤ 飞书实测硬上限」；② 撤掉修复必须变红的**变异清单**固化在 `tests/mutate_check.py` 里，
不再依赖某一轮审计的临时脚本。

**推论 8：「空集 / 空列表 = 一切正常」型断言没有判别力 —— 要让被观测对象**真的缺东西**。**
`probe_report(真适配器)["missing_reactions"] == []` 看着在守「上游改名会报警」，
但把 `probe_report` 改成恒返回 `[]`（探测彻底失效）它照样绿。做法：**拿一个什么都没有的类
去探**，缺什么就必须如实报出什么。同理，「报告里**没有**这个键」与「这个键是空列表」
必须分开 —— 前者是探测失效，后者才是契约齐全。

**推论 9：门禁自己的「覆盖清单」不能是硬编码字面量。** `check_override.py` 里那份
「要检查哪些覆盖」的名字列表原来写死，从里面删掉 `_reactions_enabled` 没有任何门禁看得见
（第七轮实测全绿）。做法：清单**从 `compat` 的登记表派生**，单一事实来源只有一处。

**推论 5：跨会话的状态写入必须在「归属」这一层就被挡住，而不是靠渲染时兜。**
`/stop` 的中止状态曾被打到**另一个会话**上：因为 `mark_stopped` 复用了「渲染用」的归属判据，
而那条判据允许「绑定的会话暂时没内容 → 退回最近活跃」。教训：**有绑定就是有归属**；
「暂时没内容」的表现应该是「这张卡没有面板」，绝不能是「换一个会话」。
同理，需要写状态的那条路径（`/stop`）应当**直按绑定取会话**，而不是借渲染的判据 ——
借来的判据会把它自己的宽松条件一起带进来。

**推论 3：状态类字段的「优先级」比取值更难，且错得很安静。** 回合结局要按
`interrupted > failed > completed` 判 —— 官方 `completed` 的表达式
（`agent/turn_finalizer.py`）里**没有** `interrupted`，所以「被中止但已产出部分正文」
的回合会同时 `completed=True, interrupted=True`；先看 `completed` 就会把中止显示成绿色
「已完成」。而这类错误肉眼几乎看不出来（谁会盯着「中止的那次是绿的」？）。
凡是「多个布尔标志合成一个状态」的地方，都要把优先级写成一行注释 + 一条门禁断言。


## 三、两个验证盲区

- **`install.sh --copy` 的 `FILES` 数组是手写的。** 新增模块漏同步会装出一个「少了指标采集
  和钩子订阅」的插件 —— 而**默认软链模式永远测不出来**，只有 NAS 会中招。
- **配置键有两处真相**：文档写的路径、代码真正读取的路径。曾经文档写
  `plugins.larkdeck.*`，代码里却没有任何读取路径，静默空转。`check_override.py`
  目前是唯一端到端断言这件事的地方。

## 四、交付约定（此前只活在 commit message 里）

每个 commit 的 message 末尾附一行**实测**门禁结果：

```
测试：91/91 · OVERRIDE OK · HOOKS OK · CLARIFY E2E OK
```

改过卡片结构就再加 `probe_render 真机 N 卡 code=0`。只写跑过的；没跑就写没跑。

**只报实测结论**：门禁数字、变异测试矩阵（「把修复回退就变红」）、真机返回码。
描述性总结（「应该没问题」「逻辑上是通的」）不算结案证据。
