# v0.7.6 — Hermes 0.21.4 延迟平台兼容

## 这一版解决什么

Hermes 0.21.4 把 bundled 平台插件改成了 **deferred loader**（启动时不导入，第一次查找时才加载）。
LarkDeck 的 `register()` 需要拿到内置 `feishu` 适配器工厂来做覆盖层；旧实现直接调用
`platform_registry.get("feishu")`。在插件加载器的新 deadline worker 里，这个调用会和主线程
持有的 discovery RLock 互等：

- 主线程持有锁，等在 worker 里执行的 LarkDeck `register()`；
- LarkDeck 拿内置平台 → 触发 deferred loader → deferred loader 也要这把锁；
- 双方互等到 `plugins.load_timeout_seconds`（默认 10s）超时，Hermes 丢弃 LarkDeck 的
  平台注册，飞书退回内置纯文本。

之前本机曾临时用 `plugins.load_timeout_seconds: 0` 绕过；那是以全局关闭插件超时保护为代价。
v0.7.6 把修复放回插件侧，配置恢复默认 10s。

## 兼容策略

`register()` 现在通过 `_resolve_builtin_platform_entry()` 分三条路径拿内置 entry：

| Hermes 版本 / 状态 | 路径 | 行为 |
|---|---|---|
| 老版 Hermes（无 `snapshot_registration`） | 回落 `platform_registry.get()` | 与 v0.7.5 以前完全一致；当时没有 deferred loader，不存在死锁 |
| 0.21.4+，内置平台已是具体 entry（热进程 / 已解析） | 直接复用 | 不触发任何额外加载 |
| 0.21.4+，内置平台是 deferred | 从 `compat.BUNDLED_FEISHU_PLATFORM_MODULES` 直接导入 bundled 模块，调用其 `register()` 捕获 `register_platform` 全量参数 | 不经过 registry 锁，entry 字段保真（`check_override` 逐字段核对） |

捕获失败时（未来上游布局再变）插件会**快速失败并自报**，不会把主线程拖进 10s 死锁，也不会静默丢平台。

## 安装 / 升级

- 已安装用户：`git pull`（或更新到 `v0.7.6`）后重启 gateway。
- 本机部署：`~/.hermes/plugins/larkdeck` → `~/Code/larkdeck/.deploy`，指向 tag `v0.7.6`。
- 回退：`git checkout v0.7.5` 后重启 gateway。
