# larkdeck v1.0 规划与分阶段实施方案（2026-09-13）

> 目标：在**不改 Hermes 源码、不 monkeypatch** 的前提下，把调研中【建议做】+【可以做】的功能
> 与「阶段 10（流式期间的元素级写入）」一起做完，然后**首次发布 v1.0.0**，并把 Mac 本地插件
> 同步生效。本文是**方案**：先经多路 Agent 审计确认可行，再逐阶段实施。

## 0. 已确立的事实（方案的地基，全部真机实测或源码核对）

| 事实 | 证据 |
|---|---|
| 关流式会话的只有**整卡替换**（`message.patch` / `card.update`）与显式 `settings(streaming_mode=false)` | `tests/probe_ck_stream_ops.py` 矩阵，5 个操作全 `code=0` 后仍可写；只有关流式那步得 `300309` |
| 流式期间 `card_element.create/patch/update`、`card.batch_update` **可用且不关会话**，且**客户端真的渲染** | 同上 + 用户肉眼确认（新增元素、面板黄边、面板内容更新三条都画出来了）|
| `card.settings` 只写 `summary` 不关流式；`summary` 必须是 i18n 对象 `{"content": …}` | 探针实测：字符串得 `300122`，对象 `code=0` |
| 字节硬上限 128000（160000 被拒 `230025`）；元素上限 200；2.0 卡 API 读回恒为 173 字节占位 | 早期真机阶梯实测（`--bytes` / `--elements`）|
| Hermes 公开插件面：`register_platform` / `register_hook`（含 `pre_command`、`gateway_platform_event`、`transform_tool_result` 等）/ **`register_command`** / **`register_approval_transport`** / `register_tool` / `register_middleware` | `hermes_cli/plugins.py` 逐个 `def register_*` 核对 |
| `register_command` **拒绝**与内置命令冲突（`/model`、`/new`、`/stop` 都拿不到） | `hermes_cli/plugins.py:652` 的 `resolve_command(clean) is not None → skip` |
| cron 结果投递走平台发送路径（`cron/scheduler_delivery.py` → `_send_to_platform` / live adapter） | 源码核对；**是否已渲染成我们的卡待真机确认**（阶段 0 探针）|
| `gateway_platform_event` 当前只有 Telegram / Discord 有 fire-site，**飞书没有** | `hermes_cli/plugins.py` 注释 |
| 点击回调可以**内联返回一张卡**（`P2CardActionTriggerResponse` + `CallBackCard`）| 官方 `_on_card_action_trigger` 里的 `_card_response(card_data)`；SDK 类公开可用 |

## 1. 范围：做什么、不做什么

### 做（对应调研 ROI 清单）

【建议做】1 长回答自动拆多卡 · 2 流式期间的元素级写入 · 3 撤回/删除守卫 ·
4 markdown 卫生 · 5 专用重试车道 · 6 卡片 summary 随进展 · 7 入站心跳自检 · 8 递归统计元素

【可以做】9 点击即回卡 · 10 澄清三态 + 重试提交 · 11 运行态标题副标题 · 12 页脚扩展
（成本/缓存命中/API 次数/图形条）· 13 命令卡（**我们自己的** `/larkdeck`）· 14 图片处理

### 不做（每条都有依据，不是"懒得做"）

| 不做 | 依据 |
|---|---|
| 接管 `/model`、`/new`、`/stop` 做交互卡 | 框架层禁止：`register_command` 与内置命令冲突直接 skip。想接管必须改源码/私有 API ⇒ 违反不变量 1 |
| cron / 后台任务的**流式进度卡** | 没有公开事件源（`gateway_platform_event` 飞书无 fire-site，钩子表里没有 cron 事件）。cron 的**结果投递**另说（阶段 0 验：若已走我们的卡，就等于已经有了） |
| 群成员 SQLite + 群内权限体系 | 与「私人 DM」场景无关，且引入持久化与隐私面 |
| 动态二次元台词库 | 口味 + 与现有双语 i18n 体系重复 |
| 可视化配置工作坊（写 `~/.hermes/config.yaml`） | 我们只经官方 `ctx.get_config()` 只读；写回配置越权且与 Hermes 配置管理打架 |
| 多 bot / 多 profile | 单机单机器人用不到 |
| 照抄它们的 28~30KB 预算 | 我们实测 128000；照抄会白丢 4~7 倍内容 |

### 待阶段 0 探针决定（**不预设结论**）

- 元素级接口的**限流/配额**（每次能打几个、每秒几个）→ 决定每帧写几次。
- 流式期间能否改 **card header（标题/副标题）**（2.0 卡 header 有没有可寻址的 element id）→ 决定「运行态标题副标题」能不能做成 cardkit 版。
- `CallBackCard` 内联换卡在**真机**是否生效（多端同步语义）。
- cron 结果是否已经渲染成我们的卡。
- `register_approval_transport` 的完整契约（能否让我们提供**审批卡**；官方意图是什么）。
- 多元素面板的**元素计数口径**（含嵌套，递归数 `tag`）与一次 `card_element.create` 能加几个元素。

## 2. 分阶段实施（每阶段独立可停、可回滚）

> **每阶段的固定收口动作**：① 四门禁全绿；② 新增断言各配一条变异并**逐条验红**；
> ③ 改卡片结构必跑真机 `probe_render.py`（默认 + `--stop-redraw` + `--cardkit-prod` +
> `probe_ck_stream_ops.py`）；④ 阶段末由**另一个子 Agent** 做对抗性代码审计，问题清零才进下一阶段；
> ⑤ commit（message 末尾附当次实测门禁数字），合适时 push。

### 阶段 0：可行性探针（只加探针，不改生产行为）
**交付**：把上面「待定」六条各写成一个可重跑的真机探针（并入 `tests/probe_ck_stream_ops.py`
与 `tests/probe_render.py` 的新模式）。
**出口条件**：六条各有一句明确结论（可做/不可做 + 数字）。**结论写进本文**。
**风险**：探针会往 DM 发卡 ⇒ 一律默认自动清理，`--visual` 模式才留卡并明确告知。

### 阶段 1：元素表基建（**行为必须逐字节不变**）
**交付**：回合状态里维护「本卡有哪些元素 + 下一个序号」；把「每帧写 2 个元素」重构为
「按元素表写」；抽出 `_ld_ck_apply(ops)`（统一处理 sequence/uuid/失败回滚/限流退避）。
**门禁**：现有全部断言 + 新增「元素表与建实体时结构一致」「序号单调」「失败后不回滚脏状态」。
**出口条件**：真机 `--cardkit-prod` 输出与阶段前**逐字段相同**（建实体 1 + 发卡 1 + 元素写入 6 + patch 1）。
**回滚点**：这一阶段不改变任何用户可见行为，可直接 revert 单提交。

### 阶段 2：流式期间的**页脚**与**实时状态色**（第一个用户可见收益）
**交付**：建实体时多建一个 `footer` 元素与一个 `status` 元素；流式期间用
`card_element.patch` 更新页脚（上下文用量）与状态色（`border.color`）；收尾仍走整卡 patch。
**门禁**：`ck_panel` 式的「结构决定」跟随（哪些元素存在就写哪些）；`unified_panel: false` /
`footer: false` 时**不建**对应元素；失败 fail-open。
**真机**：`--visual` 出一张卡给用户看；`--cardkit-prod` 断言元素写入次数随配置变化。
**风险**：每帧多 1~2 次 API 调用 ⇒ 用阶段 0 量到的限流阈值定节流（只能更保守）。

### 阶段 3：面板结构化（多元素 / 工具步骤各一行 / 批次分组）
**交付**：面板从「一个 markdown 字符串」改为「一个折叠面板 + N 个子元素」；流式期间用
`card_element.create` 追加、`patch` 更新；超过阈值按「批次」分组（抄 HLS 的每 10 轮一组思路）。
**门禁**：递归元素计数（所有含 `tag` 的对象）不得超 200 − margin；降载顺序固定（先砍最老的批次）。
**风险**：元素数量增长最快的一条 → 与阶段 4 的拆卡阈值联动。

### 阶段 4：多卡拆分（长回合不再丢内容）
**交付**：元素/字节接近阈值时「**先建新卡 → 再封旧卡**」（新卡建失败则旧卡不封、降级续写）；
旧卡封存时补状态色与页脚；新卡 `sequence` 从 1 重新计数（每卡独立）。
**门禁**：拆分顺序断言（先建后封）；建新卡失败 ⇒ 不封旧卡；正文不丢（拆分点前后拼接 == 原文）。
**真机**：构造一个必然超限的回合（大量工具步骤）看是否真的续写而不是丢内容。
**风险**：最高的一条 ⇒ 单独一轮对抗审计。

### 阶段 5：健壮性（撤回守卫 + 重试车道 + 递归元素计数）
**交付**：`231003`/`1000023`/`230011` 命中即停止更新（带 TTL 缓存）；
`300313`/`300309`/`300317`/限流码各走**专用车道**（次数与间隔不同）；元素计数改递归口径。
**门禁**：每个码一条变异；撤回后**不再发起**任何写调用（断言调用次数不再增长）。

### 阶段 6：markdown 卫生与图片
**交付**：流式期间未闭合围栏/`**` 的截断处理；H1–H3 降级为 H4（消收尾跳变）；表格超限降级为
字段列表（无损优先，抄 AP 的 `Table N · Row M` 思路）；markdown 里的图片：外链下载→上传→
替换 `img_key`（带缓存与失败降级）。
**门禁**：纯字符串函数单测（这些是纯函数，最容易测）；图片路径的失败必须回落成原文链接。
**风险**：图片上传引入网络与配额 ⇒ 默认**关闭**，配置项打开（`inline_images: false` 默认）。

### 阶段 7：页脚扩展与 summary 进展
**交付**：页脚按 `footer_fields` 配置渲染（上下文 / 耗时 / 成本实报或估算 / 缓存命中 / API 次数 /
图形条三模式——`text`/`bar`/`text_bar`）；每经过若干帧用 `card.settings` 更新 `summary`。
**门禁**：字段缺失时不留空占位；成本估算要有「估算」标注（抄 ALS 的信任标注）；
`summary` 必须是 i18n 对象（`300122` 教训）。
**数据来源**：`post_api_request` 钩子载荷（我们已经读 token；新增字段先确认真实存在，缺就标 unavailable）。

### 阶段 8：交互增强
**交付**：① 点击即回卡（澄清提交后**内联返回**「已提交」卡，省一次写入）；② 澄清三态
（待提交 → 已提交 → 已确认）+「重试提交」按钮；③ 运行态标题副标题显示当前动作（stage 0 判定可行才做）。
**门禁**：点击回调的返回值形状（`CallBackCard` 的 `type="raw"` + `data`）；不改变「未授权点击忽略」；
非法/过期点击给 toast 或保持原样。
**风险**：回调路径是**同步**的（SDK 回调线程）⇒ 只做内存操作，绝不 await。

### 阶段 9：自检与命令卡
**交付**：① 入站心跳（记录最近入站时间，自检日志里报告「距今 X 秒」）；② `/larkdeck status`
命令卡（用 `register_command`；输出经我们的 `send()` 自动成为卡片）。
**门禁**：命令注册失败（与内置冲突）必须**响亮失败**（日志 + 自检可见），不能静默；
心跳只写内存。
**不做**：接管内置命令（框架禁止）。

### 阶段 10：发布 v1.0.0
**交付**：`plugin.yaml` 版本 → `1.0.0`；新增 `CHANGELOG.md`（按版本倒序，写明用户可见变化）；
README 顶部加版本与「第一次安装」；`docs/` 索引校对；打 tag `v1.0.0` 并 push；
**GitHub Release**（用 `gh` 或 API，先确认凭据）附发布说明；NAS 安装说明复核（`docs/switch-from-hfc.md`）。
**出口条件**：远端 tag 与 Release 都在；本地软链 = tag 指向的提交；网关重启后自检通过。
**风险**：公开仓库的 Release 说明不得含凭据/真实 chat_id。

## 3. 门禁与证据纪律（沿用本项目老规矩）

- 五件套：`test_units.py`（纯单测）· `check_override.py`（真加载器）· `check_hooks.py`（真钩子）·
  `check_clarify_e2e.py`（澄清 e2e）· `mutate_check.py`（变异，**改断言必跑**）。
- 真机探针：`probe_render.py`（默认 17 卡 / `--stop-redraw` / `--cardkit-prod` / `--bytes` /
  `--elements` / `--rate-limit`）+ `probe_ck_stream_ops.py`（元素级写入矩阵 / `--visual`）。
- 每个新常量/阈值都要有「实测来源 + 上界 + 必须是算出来的」三类断言（推论 12）。
- 三条已固化的断言陷阱（推论 6/7/8/17/19 + 本轮新增）自查：**别观测自己写的替身**；
  **别让断言被更早的失败顺带满足**；**锚点必须唯一**。
- 阶段末审计必须由**不同的子 Agent** 做，且审计员**只读**（改代码留在主会话）。

## 4. 上线与回滚

- 每个阶段都是独立提交，`native_transport: "patch"` 始终是**一条配置即可回退**的安全阀。
- 新交互/新网络行为（图片内联、审批卡）默认**关闭**，用配置项打开。
- 阶段 4（拆卡）与阶段 8（回调内联）风险最高：各自单独一轮对抗审计 + 真机肉眼验收。
